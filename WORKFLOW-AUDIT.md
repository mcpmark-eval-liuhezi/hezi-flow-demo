# Workflow Audit

This page documents how branches, pull requests, issues, and close-out fit together in a tidy GitHub workflow. It is part of the show-and-tell demo for the team.

## How It All Fits Together

1. **Branch** — Work begins on a dedicated working branch (e.g. `feature/audit-notes`) off the default branch (`main`). This keeps experimental or in-progress work isolated from stable code.
2. **Pull Request** — When the work is ready, a pull request is opened from the feature branch into the default branch (titled "Add workflow audit notes"). The PR is where review happens: reviewers can read the diff, leave comments on specific lines, and approve or request changes before anything merges.
3. **Issue** — Residual tasks and follow-ups are tracked as issues. A checklist issue (`Demo: workflow checklist`) captures what still needs to be done, and smaller follow-up issues can be attached as sub-issues so progress is visible inline.
4. **Close-out** — Once the checklist is complete, a comment is posted ("Checklist complete, closing this out") and the checklist issue is closed as completed, while any open follow-up issues remain active for later work.
